## تطبيق قاعدة البيانات

إضافة Supabase متصلة وقد طُبقت المهاجرات عبرها. الأوامر التالية مرجع للمزامنة والتطوير اللاحق باستخدام Supabase CLI بمصادقة المالك محليًا. لا تُرسل كلمات المرور أو رموز الوصول في المحادثة.

```bash
npx --yes supabase@2.118.0 login
npx --yes supabase@2.118.0 link --project-ref gwjcqwjgkgemrxwvojmf
npx --yes supabase@2.118.0 migration list
npx --yes supabase@2.118.0 db push --dry-run
# بعد التأكد أن المشروع وخطة المهاجرات صحيحان:
npx --yes supabase@2.118.0 db push
```

المهاجرات المحلية تحمل إصدارات السجل السحابي نفسها، مع إبقاء SQL المهاجرتين الأصليتين دون تغيير. لا تُعد تطبيق النسختين ذواتي التوقيت القديم من تاريخ Git. يجب الحفاظ على ترتيب المهاجرات. لا تستخدم reset لقاعدة سحابية موجودة. عند وجود جداول أو مهاجرات سابقة غير متوقعة راجعها أولًا، ولا تتجاوز التعارض بإصلاح سجل المهاجرات دون التحقق من SQL الفعلي.

## إعداد Auth السحابي

ملف `supabase/config.toml` خاص بالتشغيل المحلي. في لوحة Auth للمشروع السحابي:

- Site URL المحفوظ للنسخة المنشورة هو `https://nadeem-rkq4.onrender.com`. لا تستبدله بعنوان محلي عند تطوير النسخة السحابية.
- حُفظت الروابط الأربعة التالية وتُحقق منها بعد إعادة تحميل اللوحة. لم يتغير إعداد تأكيد البريد أو سياسة كلمة المرور خلال النشر.
- إعداد SMTP للإنتاج لم يُحسم. لا تعتمد على بريد Supabase التجريبي لإرسال عام؛ راجع القيود والحصص في لوحة المشروع قبل اختبار تسليم الرسائل.

```text
https://nadeem-rkq4.onrender.com/ar/auth/callback
https://nadeem-rkq4.onrender.com/en/auth/callback
https://nadeem-rkq4.onrender.com/ar/auth/callback?next=/ar/update-password
https://nadeem-rkq4.onrender.com/en/auth/callback?next=/en/update-password
```

لاختبار النسخة المنشورة افتح `https://nadeem-rkq4.onrender.com/ar/signup`. روابط localhost ليست ضمن قائمة السحابة الحالية؛ اختبر التطوير المحلي باستخدام حزمة Supabase المحلية أو أضف وجهات تطوير منفصلة بعد اعتمادها. افتح رابط التأكيد أو الاستعادة في المتصفح نفسه الذي بدأ الطلب؛ PKCE يعتمد على cookie ذلك المتصفح. لا تتبادل `localhost` و`127.0.0.1` خلال التدفق. عند اختيار نطاق آخر يجب تحديث ملف البيئة وقائمة الروابط والبناء معًا.

## المسؤول ومراجعة المرشدين

لا يوجد مسؤول افتراضي أو كلمة مرور أولية. لا تحول كل مالك مشروع أو حساب أول إلى مسؤول تلقائيًا. بعد تسجيل حساب مسؤول مخصص وتأكيد بريده، يعيّن مالك قاعدة البيانات الدور لحساب UUID محدد ومتحقق منه خارج نموذج التسجيل. يجب أن يكون ذلك قرارًا مقصودًا؛ ليس جزءًا تلقائيًا من المهاجرة.

بعد التعيين تظهر صفحة `/ar/admin/guides` لذلك الحساب فقط. المرشد يحفظ ملفه ويرسله من `/ar/account`. المراجعة تتطلب سببًا وتسجل القرار في `audit_logs`. المعتمد والمعلّق مقفلان للتعديل؛ الملفات لا تنشر للزائر ولا تصبح قابلة للحجز في هذه المرحلة. معايير الاعتماد والمستندات تحتاج قرارًا قبل مراجعة مرشدين حقيقيين.

## التحقق بعد الربط

1. راجع سجل المهاجرات الثلاث وRLS، وتأكد أن الزائر لا يستطيع قراءة الجداول الخاصة.
2. بحسابات اختبار تملكها: سجّل سائحًا ومرشدًا، أكد البريد، وسجّل الدخول والخروج واستعد كلمة المرور.
3. تأكد من تجديد الجلسة وعزل بيانات المستخدمين عبر Auth/REST الحقيقيين.
4. راجع ملف المرشد من حساب مسؤول مخصص؛ تحقق من السبب وسجل القرار ورفض التعديل بعد الاعتماد.

اختبارات PostgreSQL المحلية لا تحل محل هذه الفحوص لخدمة Auth والبريد الفعليين.
