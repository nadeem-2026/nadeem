## النتائج

- الجداول الأربعة (`platform_settings`، `profiles`، `guide_profiles`، `audit_logs`) لديها RLS مفعّل وإجباري.
- لا وصول قراءة للزائر لأي منها. دور `authenticated` يملك SELECT على جداول الحسابات وفق RLS، دون صلاحيات تعديل مباشرة.
- نُقلت تطبيقات دوال الحفظ والمراجعة ذات الصلاحية المرتفعة إلى `private` مع الحفاظ على فحص هوية المتصل ودوره وحالة حسابه وتأكيد بريده. واجهة RPC العامة أصبحت `SECURITY INVOKER`؛ استدعاء التنفيذ الخاص يتطلب EXECUTE للمستخدم المسجّل وتظل فحوص الأعمال داخله إلزامية.
- أُضيف فهرسان للمفاتيح الخارجية `guide_profiles.reviewed_by` و`audit_logs.actor_id`.
- نجحت **26 حالة اختبار محلية** بعد الإصلاح، ونجح `npm run lint`. نتائج البناء والأنواع و24 اختبار متصفح للواجهة في تقرير الحسابات السابق؛ لم تتغير واجهة التطبيق في هذا التحديث.
- نُفذ `tests/integration/hosted-accounts.sql` على المشروع نفسه: اختبار أدوار وصلاحيات وRPC وسجل مراجعة وتعليق حساب داخل معاملة. أعاد PASS ثم ROLLBACK. أُعيد فحص عدد مستخدمي Auth والملفات والمرشدين وسجل القرارات: **صفر في كل منها**. لا بيانات اختبار باقية ولا مسؤول تطبيق عُيّن فعليًا. قد تتقدم قيمة sequence أثناء اختبار ثم ROLLBACK؛ لا يعني ذلك وجود سجل باقٍ.
- فحص REST بالمفتاح العام: الجداول الأربعة ودالتا RPC رفضت الزائر بـHTTP 401 / `42501`. طلب مخطط `private` رُفض بـ406 / `PGRST106`، ما يؤكد أنه غير مكشوف في Data API.
- Auth settings يستجيب بـHTTP 200 وتأكيد البريد مطلوب.

## نتائج Advisors المتبقية

لا تحذيرات WARN أو أخطاء ERROR في فحوص الأمن والأداء بعد الإصلاح. بقيت ملاحظات INFO مقصودة أو متوقعة في قاعدة جديدة:

- [RLS مفعّل دون سياسة](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) على `platform_settings`: مقصود لمنع وصول العميل، مع سحب grants؛ لا تضاف سياسة سماح لإخفاء الملاحظة.
- [فهارس لم تُستخدم بعد](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index): قاعدة جديدة بلا بيانات تشغيلية. لا تُحذف فهارس قائمة المراجعة أو العلاقات لهذا السبب وحده.

## ما لم يُختبر أو يُفعّل

اختبار SQL يحاكي هوية الجلسة داخل معاملة؛ لا ينشئ JWT ولا يختبر تسليم البريد أو cookies أو تجديد جلسة Auth. لم تُرسل رسائل تسجيل أو استعادة ولم يُنشأ حساب تطبيق حقيقي. إعداد Site URL وقائمة redirect URLs وSMTP لا تتيحه أدوات الاتصال الحالية، لذلك لم يُدّعَ تغييره أو التحقق منه. خطواته موثقة في `ACCOUNTS_SETUP.md`.

بعد ضبط إعدادات Auth: يختبر المالك التسجيل وتأكيد البريد والدخول والاستعادة في المتصفح نفسه باستخدام حساب يملكه. يحتاج تعيين مسؤول التطبيق حسابًا محددًا مؤكد البريد وقرارًا صريحًا. لا تزال معايير وثائق المرشدين والبريد الإنتاجي والدفع والنشر معلقة.

مراجع المراجعة: [حماية Data API](https://supabase.com/docs/guides/api/securing-your-api)، [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)، [سجل تغييرات Supabase](https://supabase.com/changelog).
